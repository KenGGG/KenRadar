## 0. 本轮决策与开发边界

本轮目标是把 KenRadar 做成适合个人 Windows 电脑长期运行的轻量应用：不再要求安装 PostgreSQL；日常通过 Web 完成订阅、处理、阅读、设置和维护；继续保留可追溯内容、持久任务、失败恢复与独立发布能力。

数据根目录可在初始化时设置，所有相对路径相对于明确的数据根或仓库根解析，不依赖当前 shell 工作目录。数据库路径不能热切换，也不能因为新路径不存在就静默创建一个空库并把旧数据“变没”。明确区分新安装初始化与迁移已有数据。

运行中的 SQLite 只放本机普通磁盘目录。不放 NAS、SMB 共享、OneDrive/Dropbox 等自动同步目录，不让 Windows 与 WSL/Docker 同时直接打开同一个数据库文件。NAS 仅保存完成且校验过的备份快照。

### 2.2 默认进程与并发

- 一个 Web 进程，一个常驻 worker 进程；调度器只归 worker 管理。
- Web 不再启动第二套采集调度器，生产模式不使用会重启多份进程的开发 reload。
- Web 负责查询、设置和任务入队；worker 负责长任务，下载和 ASR 不在 HTTP 请求中同步等待。
- 首版下载并发建议 2，重型 GPU 阶段并发 1，AI 整理按已有 provider 限流排队。数值是保守默认值，需实测调整。
- 定时扫描以“来源 + 计划时间窗口”等稳定键去重；重复启动不会重复入队。
- 长任务可以并行计算，但数据库写入只采用短事务；不增加一个独立数据库服务来包装 SQLite。

### 2.3 环境与启动

先检查 `D:\Users\ken\miniforge3` 等已知位置，确认解释器实际存在与可运行，不把 PATH 未发现当作未安装。KenRadar 使用独立环境，不修改 QMT、QuantRadar、OARadar 等其他项目的环境。

统一 `pyproject.toml` 为依赖声明源，生成锁文件；`requirements.txt` 如需保留，应由相同来源导出。拆分 core、ASR、开发测试、PG 迁移等可选依赖，正常启动不能 import psycopg。锁定实际通过验证的 Python、SQLite、CTranslate2、PyTorch 和前端组合，不盲目执行全量 latest 升级。

提供 Windows 安装、启动、停止、状态、诊断脚本。内部启停逻辑尽量复用 Python 管理模块，PowerShell 只作为入口。修复 `fcntl`、`/tmp`、`/proc/meminfo`、绝对解释器路径、Unix 信号、shell 启停命令和前端 `rm -rf`。文件锁统一封装并使用 portalocker 等跨平台实现，GPU/配置/服务启动/Git 同步锁不得静默降级为进程内锁。

停止 worker 必须处理子进程、心跳和租约，避免只关闭父进程而留下 FFmpeg/ASR。HTTP 服务默认绑定 `127.0.0.1`，不自动暴露到局域网或公网。

## 3. SQLite 技术规格

### 3.1 连接、事务和运行库检查

初始目标配置：

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = FULL;
```

`journal_mode` 在数据库初始化或受控维护阶段设置并检查返回结果；外键、超时和同步等级通过连接初始化统一配置。外键 PRAGMA 必须在正确的事务时机设置，并验证每个连接确实启用。默认 FULL，不以关闭同步或关闭外键换取测试通过。

SQLite WAL 仍然一次只允许一个写事务。所有网络访问、模型加载、下载、推理、Git push、等待重试都必须放在数据库事务外。普通读操作不能一律用 `BEGIN IMMEDIATE`；需要先读后改的任务领取等短写操作才使用该方式。

显式管理 SQLAlchemy 与 sqlite3 的事务：可以采用 SQLAlchemy begin 事件统一发出 BEGIN，并通过数据库封装选择 DEFERRED 或 IMMEDIATE；不得同时混用互相冲突的 autocommit 设置，也不得在已有自动事务中再次执行 BEGIN。必须通过实际事务回滚、DDL、savepoint 和并发测试。

一个业务原子操作中的任务、attempt、state_transition、outbox 更新必须复用同一连接。重点排查外层写事务内再次调用 `database.connect()` 建立另一条写连接的自锁问题。不要靠全局共享连接或 `check_same_thread=False` 假装解决并发。

对 BUSY/锁竞争做有上限的等待与退避；需要重新读取状态时重试整个小事务，而不是盲目重放最后一条写语句。外部调用不在数据库重试函数内部。

启动诊断应实际检测 Python 所加载的 `sqlite3.sqlite_version`、JSON 函数、FTS5、WAL、外键、读写权限和磁盘空间。官方已修复 WAL-reset 并发问题：正常基线建议使用 3.51.3 及以上且经过验证的维护版本；更早的官方回移修复版本只有在明确列入测试矩阵时接受。不能只检查 `sqlite3.exe` 的版本，也不能从不可信来源随意替换 DLL。

### 3.2 保留业务模型，逐项重写 SQL

继续保留来源、作者、内容、转录、分析、笔记、任务、资源租约、发布/通知及审计之间的关系。不得仅迁移“内容表”而丢弃处理与交付历史。

重点包括但不限于：`platform`、`creator`、`source_subscription`、`content_item`、`transcript`、`ai_analysis`、`content_note`、`research_job`、`research_job_item`、`task_run`、`task_attempt`、`task_step`、`state_transition`、`artifact`、`outbox_event`、`resource_lease`、`publication_log`、`push_log`、`alert_log` 及实际存在的洞察表。

| 原实现 | 新实现要求 |
| --- | --- |
| psycopg pool / `%s` | SQLAlchemy Core/绑定参数，保持返回字段契约 |
| BIGSERIAL / identity | SQLite 正确的 INTEGER 主键策略，迁入后新增 ID 不冲突 |
| JSONB | JSON 文本与类型校验；读取恢复为原 dict/list，保留 NULL、空对象、空数组区别 |
| TIMESTAMPTZ / NOW / INTERVAL | 固定格式 UTC 存储和统一时间工具；保留原时间精度与瞬时时点 |
| ILIKE、数组、JSONB 查询、修改 CTE、PG 视图和函数 | 逐条建立等价实现和边界测试，不能正则替换后声称完成 |
| `FOR UPDATE SKIP LOCKED` | 短写事务内选取、条件更新、提交后执行 |
| upsert/去重 | 明确唯一约束和冲突目标；不能用 REPLACE 隐式删除重建关系 |

外部内容 ID、视频 ID、作者 ID、股票代码等标识保留字符串语义，避免经 JavaScript Number 丢精度或丢前导零。内部整数超出 SQLite 范围必须报错，不截断。日期采用固定精度 UTC 文本等唯一规范，禁止同列混用本地时间和 UTC；展示与计划执行保留明确的 IANA 时区。迁移继承原计划时区，不因新电脑系统时区改变而重设。

保留原 API 的状态枚举、分页、排序、过滤和空值语义。新的 UI 标签可以更友好，但不得随意改写已有状态含义。

### 3.3 任务领取、租约和结果提交

任务领取以如下语义实现，而不是要求照抄某条示例 SQL：

1. 开启短 IMMEDIATE 事务，回收符合条件的过期任务；同步关闭孤立 attempt 并记录审计。
2. 按已有优先级、可执行时间、创建时间和 ID 选择一个可执行任务。
3. 条件更新为 running，生成本次租约 token/attempt 标识并设置期限、owner 和心跳。
4. 写入本次 attempt/状态转换，提交事务。
5. 在事务外执行下载/转录/整理；心跳使用独立的短事务。
6. 只有 task ID、租约 token/attempt、owner 和当前可提交状态均匹配时，才允许续租、提交结果或报告失败。

租约丢失的旧 worker 即使恢复，也不得覆盖新 worker 的结果。所有相关结果写入必须检查租约，不仅检查任务表最后的 success 更新。

保留暂停、继续、取消、失败重试、断点和最大尝试次数。进度有真实总量时才显示百分比；没有总量时显示阶段和耗时。应用启动不把历史 running 直接改成 success，也不把所有成功任务重新入队。

本地结果通过唯一键与事务实现幂等。GitHub/飞书等外部行为存在“已经发送但本地未记录”的崩溃窗口，不能宣称绝对 exactly-once。结果不确定时记录待核状态；有远端查询依据则核对，没有则不自动盲发。

### 3.4 Schema 演进

冻结原 PostgreSQL 迁移文件，保留源版本识别和历史重建用途。SQLite 使用单独且明确的 baseline/env/version 管理，由本轮已核对的业务模型创建；后续 SQLite 变更仍走 Alembic，必要时使用 batch migrations。

不能让 SQLite 直接执行 PostgreSQL 历史迁移；不能仅 `create_all()` 再随意 stamp 为旧 PG head；不能留下两个都声称是当前 SQLite schema 的版本源。

正常运行不长期维持两套数据库后端。PG 读取器放入迁移工具和可选依赖；旧版回滚使用归档代码与旧数据库，不以在新程序里永久保留 PG 运行分支为默认方案。

## 4. 真实数据迁移与回滚

### 4.1 两步迁移，避免在新电脑安装 PostgreSQL

提供两个可分别执行的步骤：源端只读导出，目标端离线导入。源端可以是旧 Ubuntu、可访问的旧 PG，或用于恢复备份的隔离 PG 实例。只有 `.dump` 文件时先通过 PostgreSQL 正规恢复再导出；SQLite 不能直接读取 PG 自定义 dump。

导出包建议包含：格式版本、代码/schema 版本、快照信息、表清单、字段类型、逐表行数、逐表校验值，以及 JSONL/其他明确类型编码的记录。JSONL 内数字、时间和二进制编码必须明确，不允许 float 往返损失精度。

一次导出要获得一致性数据库快照；最终正式导出还必须暂停原系统所有写入和文件产物生成，确保数据库与笔记文件对应。不要在持续写入的生产库上逐表获得不同时间点数据后称之为一致备份。

### 4.2 导入要求

导入到全新临时文件，例如 `data/migration/kenradar.importing.sqlite3`，不是直接覆盖目标生产库。

保留全部主键、自然键、外键关系和幂等键；按依赖顺序导入，循环关系专门处理。必要的 schema/索引重建有独立步骤。中断恢复以 manifest、表范围和明确批次检查点实现；重复执行不得重复记录。

同步迁入笔记、简报及所需历史产物并验证文件哈希。迁移绝对路径时使用“旧根目录 → 新根目录”的明确映射，仅改写路径字段；不能对正文、URL 和 JSON 全文做无差别字符串替换。原视频已经按规则清理不是数据迁移失败，但必须与真正缺失的笔记/产物分开列报。

历史成功发布/通知保留成功审计与公开链接，不重发。旧运行中任务做可审计的失效恢复；排队的公开发布和通知迁移后默认暂停，由用户检查后恢复，不因为启动新 worker 而突然外发。

### 4.3 必须输出的验证结果

| 项目 | 通过标准 |
| --- | --- |
| 表覆盖 | 所有实际表已迁移或有明确、经确认的“不迁移”理由 |
| 数量 | 逐表数量、按平台/状态分类数量一致；规范化转换单独列示 |
| 身份与关系 | 主键集合、自然键、外键、唯一键无未解释差异 |
| 内容 | 原始转录、分析 JSON、笔记正文规范化校验一致；不能只验行数 |
| 交付历史 | 发布地址、通知记录、幂等键一致，无重复发送 |
| 文件 | 路径映射和文件哈希可核对，缺失清单明确 |
| 数据库 | integrity_check 返回 ok，foreign_key_check 无异常 |
| 行为 | 同一组 API 请求在迁移前后具有等价业务输出 |

保留现有只读核对脚本的业务价值，改造为支持 SQLite 的核对入口，而不是删掉不兼容检查以通过验收。

### 4.4 切换与回滚

正式切换前保留原库、原配置、原代码版本和文件快照。临时库通过验证后，在程序停止且所有连接关闭的情况下进入目标位置，切换唯一配置并启动只读/无外发验收，之后才恢复处理。

严禁两套系统同时作为权威写入端。开始在 SQLite 产生新数据后，直接切回旧 PG 会缺少新数据；此时必须先冻结并保存 SQLite 新增数据，明确补迁方案，不能承诺“一键切回且自动不丢任何新增数据”。本轮不建设长期双写或双向同步。

缺少旧库或备份时，继续完成新库、fixture、迁移工具和界面开发，并把真实数据迁移标为“待真实源验证”，不得捏造数量、比对结果或使用空库代替真实迁移成功。

## 5. 备份与存储维护

运行中 SQLite 使用官方 backup API/等价受控快照机制，不只复制 `.sqlite3` 主文件，不删除 `.wal` 或 `.shm` 来消除错误。

区分“数据库快照”与“完整应用备份”：后者还包含 notes、briefs、非敏感配置、版本信息和文件哈希 manifest。在备份窗口暂停相应文件与配置写入，避免数据库快照和文件来自不同时点。密钥、Cookie、浏览器认证状态不进入普通导出包；需要转移时采用独立的本地敏感资料流程。

设置页提供备份、校验、查看位置和恢复入口。默认保留最近若干备份并允许修改策略，自动备份时段明确。恢复在停止写入后对临时目标执行，先校验再替换；不在 Web 请求里直接覆盖正在打开的数据库。NAS 上只保存闭合且校验过的备份包。

维护信息包括数据库/schema/SQLite 版本、DB/WAL 大小、磁盘余量、最后备份与最后校验时间。普通用户不需要调整 PRAGMA；WAL checkpoint 在合理空闲窗口处理，不逐条写入强制 TRUNCATE，不由每个进程重复执行重型维护。

## 6. 新版前端的信息架构

保留现有 React/Vite 工程，不从模板覆盖整个 src。新版定义六个清晰入口：

| 入口 | 主要任务 | 明确边界 |
| --- | --- | --- |
| 今日雷达 | 查看新内容、值得阅读内容、需要处理的问题 | 不是 CPU/GPU 仪表盘 |
| 内容库 | 搜索、筛选、阅读、查看来源证据和当前结果 | 是阅读主入口，不混入完整运行日志 |
| 订阅来源 | 添加来源、管理订阅、扫描新内容、预览历史范围 | 来源账号凭据在设置中，避免重复配置 |
| 新建处理 | 粘贴分享链接、导入本地音视频、预览并创建任务 | 不自动变成无界批量抓取 |
| 任务中心 | 执行队列、待处理、批次历史、发布通知与系统诊断 | 技术监控收进二级页，不新增多个重复一级页 |
| 系统设置 | 初始化、账号、模型、自动运行、存储、发布和安全 | 普通设置表单化，高级参数默认收起 |

当前 `/content?platform=...&external_id=...` 内容定位方式继续兼容；现有路由、书签、外部引用与批次 URL 建立对应关系和 alias，不因换名字让历史链接失效。不要把“批次处理来源”重新扩展成已退役的深度研究产品。

### 6.1 视觉规范

默认浅色：浅灰背景、白色内容面板、少量蓝色强调；保留现有深色切换，不让深色设计阻塞核心功能。色彩、间距、边框、圆角和状态统一由 design tokens 控制，不能每个页面手写一套。

桌面采用约 220–240px 左导航、清晰顶部标题/搜索/主操作区。内容区域优先列表而非密集大卡片；文章正文 16–18px，行高约 1.7–1.8，阅读宽度约 760–900px；桌面内容库可“列表 + 预览”，窄屏回到列表与独立详情页。

不使用大面积渐变、玻璃效果、无意义动画和巨型统计数字。每页主要操作不超过两个；删除、重跑、公开发布等分开摆放。状态不仅靠颜色，必须有文字。保留键盘焦点、表单 label、合理对比度、加载/空/错误/无权限/未配置状态。

### 6.2 今日雷达

顶部只保留少量业务数字，例如新增、已生成笔记、待处理、待人工处理；定义清楚统计时间窗口和计算对象。页面主体是内容推荐列表、来源更新和少量需要行动的事项。

全部角标与统计由后端聚合，带统计时间；不得使用当前页 items.filter 充当全库计数。刷新失败显示“数据暂时不可更新”和最后成功时间，不把原有数据归零伪装正常。

### 6.3 内容库与详情

支持服务端搜索及平台、来源、日期、主题、处理质量、发布状态的组合筛选；分页、排序、筛选条件写入 URL，返回列表保留位置。列表不加载所有长转录。标题、作者、日期、摘要和状态优先，技术细节进入详情。

详情继续保留四段笔记：一、内容简述；二、分段原文；三、知识关联；四、视频原始转录。原始转录默认折叠，显示转录引擎、整理模型、时间、原链接和质量警告。重新整理与重新转录是不同动作；新的结果验证失败不能覆盖已有有效结果。

分别展示处理状态、内容质量、公开发布状态和通知状态，不能合并成一个 success/failed。笔记成功但 Pages 失败，应显示“笔记可阅读，发布待重试”，不能诱导用户重跑 ASR。

### 6.4 订阅与新建处理

添加来源采用“输入 → 解析预览 → 调整名称与范围 → 保存”的流程。添加订阅不立即下载全部历史；首次历史扫描先列出候选数量、日期、已处理数量和预计动作，再由用户确认选中范围。

抖音支持完整分享文本并从中正确抽取链接；小宇宙保留有效 query 参数。输入已在运行的内容时返回现有任务入口；已完成内容默认复用结果，重处理需要明确动作。

本地文件导入进入同一内容/任务链路，允许补充原始链接、标题、作者和日期，不形成第二套独立文件资料库。浏览器的文件选择仅代表上传，不假装获得任意 Windows 目录的真实路径；服务器端路径选择/打开目录必须有受控实现与权限边界。

### 6.5 任务中心

以真实持久任务为核心，设置“执行中/排队、待处理、批次与历史、发布通知、系统诊断”等二级视图。每项默认显示内容、阶段、状态、耗时和下一步；技术日志与错误堆栈展开后看。

区分登录失效、平台校验、网络故障、模型缺失、运行库缺失、显存不足、AI 限流、发布失败等原因。恢复动作应直接到对应设置或对应失败阶段。需要人工处理的错误不能无限自动重试。

## 7. 设置操作重做：保存、测试、生效三件事分开

### 7.1 分组

| 分组 | 常用配置 | 高级配置 |
| --- | --- | --- |
| 概览与初始化 | 初始化向导、环境状态、缺失能力、数据位置 | 诊断报告 |
| 来源账号 | 抖音登录状态、重新登录、账号测试 | 浏览器会话和代理策略 |
| 转录与 AI | 主转录引擎、兜底、运行设备、AI 主/备 provider、模型测试 | compute type、VAD、batch、超时、token、采样参数 |
| 自动运行 | 启停、每天/每周执行时间、时区、扫描范围、重试策略 | cron、限流与并发 |
| 笔记与存储 | 笔记目录、缓存保留、临时文件清理 | 路径迁移与模板细节 |
| 发布与通知 | Pages 地址、发布范围、Git 状态、飞书预览与明确测试发送 | 分支、允许发布的路径列表、提交策略 |
| 数据备份 | 备份、校验、位置、恢复引导 | 保留策略与维护 |
| 高级与安全 | 监听地址、访问保护、日志级别 | 开发选项与配置导出 |

来源订阅只在“订阅来源”编辑；设置仅管理平台账号和连接，不能复制另一份作者列表。模型配置必须对应实际 provider 能力，不展示没有实现的开关；AI 供应商不支持的 top_k 等参数隐藏或禁止填写。

### 7.2 初始化向导

首次打开先选择“全新安装”或“迁移已有数据”，再检测 Python/SQLite/FFmpeg、设置目录、导入或建库、配置转录和 AI、执行本地样本、选择是否启用订阅与发布。

未配置 GPU、某个模型、GitHub 或飞书时仍允许进入内容库和设置，显示具体能力不可用，不让整个 Web 页面被一个可选依赖阻塞。平台登录状态由实际检查给出，不以“Cookie 字段非空”判断可用。

### 7.3 表单与接口契约

各设置组独立编辑和保存。前端采用 React Hook Form + Zod 管理表单，后端 Pydantic 是最终校验源；用契约测试对齐字段、默认值和错误结构，不能长期维护两套不一致规则。

前端表单草稿和服务器快照分开。轮询/切页返回不能覆盖未保存编辑；离开时提醒。保存期间禁用重复提交；只有收到后端成功响应才显示已保存。保存失败必须保留草稿并展示字段或整体错误。

设置 API 建议具备以下语义（命名可适配既有路由，不另起重复 API）：

```text
读取：返回脱敏值、有效值来源、配置 revision、运行中 revision
校验：校验本次草稿，不落盘、不切换运行设置
测试：测试指定草稿，不保存；告知是否联网/消耗额度/发送消息
保存：按组 PATCH + expected_revision，返回新 revision 和生效方式
生效状态：立即生效 / 新任务生效 / 待重启生效，必要时显示失败原因
```

保存时检查 revision，冲突返回 409，不静默覆盖另一浏览器修改。响应含 `saved_revision`、`effective_revision`、`restart_required` 或同等清晰字段。高风险操作采用单独确认，不藏在“保存设置”内。

原有配置加载优先级先建立清单，再统一文档化为一个明确规则。CLI/环境变量覆盖的字段显示覆盖来源，不让用户在 YAML 表单里改了却误以为已覆盖环境变量。数据库路径与监听端口等需要重启/迁移的设置不可伪装热重载。

非敏感业务配置继续以 config.yaml 为唯一持久真值；不要再在 SQLite、localStorage 和 YAML 各存一份同名配置。localStorage 只保存主题、列表密度等纯界面偏好。写文件采用锁、备份和同目录临时文件原子替换。

运行任务绑定领取时的非敏感配置 revision；中途保存新配置不突然切换当前 ASR 模型或 AI provider，后续任务使用新版本。不得把 API Key 快照复制进每个任务 payload。

### 7.4 秘密与测试外发

API Key、Cookie、Webhook 密钥只允许“保留、替换、删除”三态操作。后端返回 configured/source/必要的掩码信息，不能把明文密钥返回前端再用星号遮住。空输入默认保留，不当作删除。

保留现有环境变量/.env 使用方式；写入和导出时实施权限和脱敏。普通 .env 不是加密保险箱，不作错误宣传。认证状态、密钥、数据库备份不得进入 GitHub 发布允许列表或诊断输出。

“测试 AI”明确说明会联网且可能消耗额度；“测试飞书发送”明确说明会真实发出一条测试消息。普通保存、健康检查、初始化预览不得触发推送。GitHub 连接测试默认只读/dry-run；实际 push 是另一个动作。

本地 Web 的设置和文件操作也要防跨站请求，默认同源、受控 Origin/Host 与必要会话保护；打开局域网访问时必须明确开启访问保护。后端不得拼接任意用户输入为 shell 命令。

## 8. 前端工程实施

按功能拆分 `ConfigEditor.tsx`、来源页、阅读页和任务页，建立统一 Button/Input/Select/Dialog/Badge/EmptyState/ErrorState/LoadingState/ConfirmAction 等组件。

shadcn/ui 只引入实际使用组件，不运行覆盖现有工程的脚手架命令。保留已有 Markdown 渲染、Lucide 图标与必要图表；不新增多套 UI 库和重复全局状态管理。

TanStack Query 统一服务端数据请求、缓存、变更后的刷新和错误处理。接入某个页面时移除该页对应旧轮询，防止两套逻辑同时请求。保留可用 SSE 并补断线回退；不为本轮迁移强制重写实时通信。后台标签页降低轮询频率，长文本按需加载。

建立统一 API client 和从 OpenAPI/契约派生的类型；不得通过 `as any` 大面积掩盖接口错误。原包的 lint 只是 tsc 检查，应明确区分 typecheck、lint、组件测试、构建和浏览器测试。

## 9. 内容链路的有界升级

此部分不应阻塞 SQLite/设置/界面核心版本，但在完整计划中保留独立阶段。

### 9.1 下载与字幕

继续通过现有平台适配器管理来源和下载，不把第三方下载器的数据库或调度器搬进来。抖音下载的可用性必须用当前实际账号与网络验证，更新 Cookie 或换库不构成成功证据；需要验证码时转人工，不绕过平台访问限制。

支持字幕的平台先检查字幕是否存在且质量合格，再决定 ASR。字幕区分人工、平台自动和本地转录；抖音没有可用字幕时照常提取实际视频音轨，不把背景音乐 URL 当口播音轨。只做转录时减少无意义的高画质下载，但保留真正需要画面时的路径。

完成与去重以数据库有效结果为准，不以已清理的临时媒体是否存在为准。保留本地文件导入作为合法可取得媒体的恢复路径。

### 9.2 转录与整理

保留一主一备；检查转录总开关与单引擎开关的关系，不能用 Whisper 开关误关闭整条 FunASR 路线。PyTorch 与 CTranslate2 GPU 路线分别做真实转录测试。DLL/版本不匹配与 OOM 分开识别。

保存不可变的原始转录、分段时间、文字来源、引擎/模型版本、质量和耗时；整理文本另存，不能覆盖原稿。数字、名称与否定词不确定时标记，不让模型凭常识补事实。重要摘要逐步关联原文时间或段落。

新 ASR 候选只对固定样本做对照；测试普通话、粤语/口音、中英混合、音乐背景、长播客，按关键事实准确性、漏句、幻听、耗时和峰值资源比较。未完成 Windows 实测的候选不得替换生产主引擎。

### 9.3 本地搜索与公共搜索

本地内容库采用 SQLite 查询并逐步引入 FTS5；公共 GitHub Pages 采用 Pagefind，二者分开维护权限范围。

中文首版要求普通关键词子串搜索语义明确：3 字符以上可采用 FTS5 trigram，1–2 字符及不适用查询回退受控 LIKE；特殊字符正确转义并接受可能无法用索引的回退成本。不能只启用默认 tokenizer 就宣称中文检索完整，也不能让两字词返回错误的空结果。搜索索引是可重建派生产物，不是内容主存储。

Pagefind 只索引本次允许公开的 HTML，正确设置页面语言并验证中文搜索。排除内容要同时从公开文件和索引移除；“折叠原文”与“不加入索引”都不等于保密。公共站点保持静态，不上传 SQLite、配置、浏览器认证状态、日志或模型缓存。

继续保持处理、发布和通知独立。发布失败只重试发布；通知失败不重新下载和转录。新增 UI 默认不扩大既有公开范围，也不自动重发历史内容。

## 10. 开发阶段、交付物与通过条件

| 阶段 | 工作 | 必须交付 | 通过条件 |
| --- | --- | --- | --- |
| P0：核查与基线 | 核对本地改动、SQL/配置/API/页面/数据范围、冻结业务契约 | 审计、schema 映射、路由映射、测试基线、风险清单 | 明确真实缺项；不修改生产数据、不伪造测试成功 |

| P3：设置后端与交互 | 配置 revision、脱敏、按组保存、草稿测试、生效状态、初始化 | 设置 API、分组表单、错误与冲突测试 | 保存/测试/生效互不混淆；失败不报成功、不丢草稿 |

| P5：检索与流程增益 | 字幕优先、质量来源、中文本地搜索、Pagefind、新 ASR 对照 | 搜索/流程测试、候选模型比较、发布预览 | 不破坏主线；公共内容范围无扩张；新模型未过测不启用 |
| P6：回归与正式切换 | 故障注入、长任务、升级恢复、真实小样本与切换 | 最终报告、运行手册、回滚边界、待核事项 | 数据核对和核心回归通过，真实外发按授权独立验收 |

每阶段独立提交或形成清晰 diff，测试通过后继续下一阶段，不把数据库、UI 和模型替换混成一个无法回滚的大提交。缺少账号/GPU/真实 PG 时完成不依赖这些条件的部分，并准确标记其余项，不停在只有规划文档的状态，也不把 mock 通过算作真实链路通过。

## 11. 验收矩阵

### 数据与任务

| 场景 | 预期 |
| --- | --- |
| 全新安装，不装 psycopg/PG | Web、设置、本地文件与 SQLite 任务可运行 |
| 全量迁入 + 重复执行导入 | 记录、关系、幂等键不重复；内容校验无未解释差异 |
| 两个独立 worker 同时抢任务 | 任一时点同一任务只有有效 owner；测试真实多进程/文件库，不用内存库替代 |
| 领取后进程被终止 | 过期可回收，旧 attempt 有审计，新 attempt 可继续 |
| 旧 worker 在新租约产生后恢复 | 心跳、任务状态和结果提交均被拒绝 |
| 写锁竞争、磁盘满、目录只读 | 有界失败、事务回滚、明确错误，不死循环、不错误标成功 |
| 写事务中途抛错 | task/attempt/state_transition/outbox 不出现半提交 |
| 正在备份时继续读取，随后恢复 | 快照可用，恢复后完整性和文件 manifest 通过 |
| Pages/飞书失败或结果未知 | 不重跑 ASR；未知状态不盲目重发 |

建议构造至少 1,000 个轻量任务的并发与恢复测试，以及 10,000 条内容的查询基准。数据规模和耗时是测试目标，不是声称现有系统已具有的性能。长模型请求不计入普通列表响应时间；记录真实机器、测试数据规模和 p50/p95，而不是只展示一次最快结果。

### 设置与前端

| 场景 | 预期 |
| --- | --- |
| 保存返回 4xx/5xx/断网 | 不出现成功提示，草稿仍在 |
| 两个窗口修改同组配置 | 409 冲突提示，不能覆盖别人的更新 |
| 表单编辑期间数据刷新 | 未保存字段不被服务器旧值覆盖 |
| 环境变量覆盖 YAML | 明确展示当前有效值来源和生效限制 |
| Key 留空后保存其他字段 | 旧 Key 保留；删除必须明确选择 |
| 测试未保存 AI 草稿 | 测试草稿，不落盘，不影响运行任务 |
| 修改模型时已有长任务 | 当前任务沿用既定 revision，新任务使用新 revision |
| GPU/模型缺失 | Web/内容库可用，受影响能力显示具体问题 |
| 搜索“国债”“算力”“ETF”和长词 | 结果语义正确，中文短词不被 trigram 漏掉 |
| 旧内容/批次 URL、刷新和浏览器后退 | 正常定位，筛选和列表位置合理保留 |
| 点击普通保存/健康检查 | 不发送飞书、不推送 GitHub、不自动下载模型 |
| 私有内容与秘密扫描 | 不出现在公开 HTML、Pagefind、前端 JSON、日志或发布 diff 中 |

Playwright 必须连接真实测试后端与独立 SQLite fixture，输出 1366×768、1920×1080、390×844 等尺寸的页面截图，并检查主要浏览器缩放、键盘焦点、长标题、长 URL、加载、空白、失败和未配置状态。视觉截图与交互断言同时通过；`npm run build` 通过不是 UI 验收。

CI 至少覆盖 Windows + Linux 的纯逻辑/SQLite 测试；GPU与真实平台测试作为独立可选作业，缺运行条件准确记录。fixture 与测试凭据不得指向生产数据库。
