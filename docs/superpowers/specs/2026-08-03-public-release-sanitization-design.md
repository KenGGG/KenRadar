# KenRadar 公开发行与实验功能退役设计

## 1. 目标

在不暴露私有仓库历史、配置、运行数据和个人内容的前提下，交付一个可完整部署的 KenRadar 公开发行版。同时在当前私有仓库正式退役公司研究、财务分析和 NotebookLM 实验功能，且不影响现有抖音、小宇宙/RSS、PostgreSQL、Web、飞书和 GitHub Pages 生产链路。

公开版采用 Apache-2.0 许可证，以 Docker Compose 作为首选安装方式。公开版的 GitHub Pages 继续使用独立内容仓库，由用户自行绑定，不在源码仓库中存放生成内容，也不在 GitHub Actions 中运行采集、转录或 AI 工作负载。

## 2. 非目标

- 不公开或改写当前私有仓库的 Git 历史。
- 不改变当前私有远程仓库的可见性、远程地址或分支结构。
- 不修改或迁移当前生产 Pages 仓库及其 URL。
- 不删除私有 PostgreSQL 中已有的实验功能表或历史数据。
- 不在此次工作中新增平台采集链路、权限系统或大面积 Web 视觉改造。
- 不承诺基础 Docker Compose 镜像内置 GPU、FunASR、Whisper 或 Ollama 运行环境。

## 3. 总体方案

采用“受控公开发行版”方案，分两个独立阶段实施。

### 3.1 阶段 A：私有仓库退役实验功能

在当前 KenRadar 私有仓库中删除公司研究、财务分析和 NotebookLM 的运行时代码与产品入口。保留历史数据库迁移，使已有数据库和从头执行迁移的数据库均能继续升级；保留已有表和数据，不执行破坏性清理。

### 3.2 阶段 B：生成公开发行副本

从阶段 A 验证通过的已跟踪源码生成独立目录 `/data/Projects/KenRadar-public`。公开副本不复制私有 `.git`，初始化为新的 Git 仓库。公开副本拥有独立的开源文档、容器部署文件、配置样例、CI 和发布审计工具。

在用户最终确认前，仅准备本地公开副本和本地提交；不得创建 GitHub 仓库、添加远程地址或推送代码。

## 4. 私有仓库改造边界

### 4.1 删除的运行时能力

- 删除 `kenradar/company_research/` 全部模块。
- 删除公司研究专属 storage repository 和 `pg_database.py` 运行时代理方法。
- 删除公司研究与财务分析 Web API、路由、状态查询和配置入口。
- 删除前端公司研究工作区、财务分析组件、导航入口、类型与状态处理。
- 删除 worker 中的公司研究、Notebook 清理和财务分析任务类型。
- 删除专属测试、脚本、设计材料和 README 说明。
- 从依赖声明和可选安装说明中移除 AkShare、NotebookLM 及仅为实验功能服务的依赖。

### 4.2 保留的数据库兼容层

- 保留已有实验功能迁移文件及其 revision 链。
- 保留基线 schema 中已有实验表定义，避免全新数据库执行历史迁移失败。
- 将这些迁移标注为退役兼容用途，禁止新增运行时代码依赖。
- 不新增 `DROP TABLE` 迁移，不删除或自动导出已有实验数据。

### 4.3 必须保持的能力

- 抖音来源监控、抓取、下载和研究任务。
- 小宇宙节目、单集和 RSS 研究/订阅 MVP。
- FunASR 优先、Whisper/faster-whisper 回退的转录链路。
- OpenAI-compatible organizer 与 Ollama fallback。
- PostgreSQL 状态、内容笔记、任务恢复、失败重试和调度。
- Obsidian Markdown、静态 HTML、独立 Pages 仓库同步和飞书通知。
- Web 仪表盘、内容工作台、归档研究、来源管理、来源洞察和系统监控。

## 5. 公开副本的隔离与导出

### 5.1 导出方式

公开副本必须通过显式白名单从私有仓库已跟踪文件生成。导出工具先计算文件清单，再复制允许文件，最后执行内容审计。任何审计失败都会终止初始化或更新。

公开副本不得包含：

- 私有 `.git`、远程地址、分支、标签和提交对象。
- `.env`、真实 `config/config.yaml`、Cookie、备份配置和数据库凭据。
- `data/`、日志、媒体、转录、笔记、简报和生成 Pages 内容。
- 浏览器状态、agent 状态、worktree、缓存和本地锁文件。
- 前端构建产物、Python egg-info、截图和个人研究文档。
- 当前 Pages 仓库克隆或任何已发布内容。

### 5.2 公开仓库内容

公开版应包含：

- 经过退役清理的应用源码和测试。
- Apache-2.0 `LICENSE`。
- `THIRD_PARTY_NOTICES.md` 和保留的第三方版权头。
- 面向新用户重写的 README、架构说明和部署文档。
- `CONTRIBUTING.md`、`SECURITY.md`、行为准则和变更记录策略。
- `.env.example`、公开配置模板和配置向导。
- Dockerfile、Compose 文件、健康检查和持久卷定义。
- CI：后端测试、前端检查、容器 smoke test、秘密扫描和许可证检查。
- 可重复执行的公开发行审计脚本。

## 6. Docker Compose 运行架构

### 6.1 基础服务

- `app`：运行 KenRadar Web、CLI 和后台 worker。
- `postgres`：运行 PostgreSQL，提供健康检查、持久卷和自动初始化。

应用容器使用非 root 用户。配置、`data/` 和 Pages 输出使用独立持久卷或显式宿主机挂载。默认 Web 仅绑定宿主机 `127.0.0.1`；配置非回环绑定时必须启用访问密码。

### 6.2 可选外部能力

- FunASR、Whisper/faster-whisper 和 Ollama 不进入基础镜像的强制依赖。
- 公开版支持连接外部 OpenAI-compatible ASR 和 organizer 服务。
- Agnes 与 Ollama 作为 provider 配置示例，不作为硬编码产品依赖。
- 飞书未配置时通知能力禁用，应用其余功能正常运行。
- 抖音 Cookie 未配置时，抖音诊断明确报告缺失，但小宇宙/RSS 和 Web 仍可使用。

### 6.3 最小可部署验收

新用户只安装 Docker、Docker Compose 和 Git，复制示例环境文件并填写必要值后，可以：

1. 构建并启动应用与 PostgreSQL。
2. 自动初始化或升级数据库。
3. 运行 `doctor` 并访问健康检查和 Web。
4. 在无抖音 Cookie、无飞书和无 GPU 的情况下安全启动。
5. 配置通用 OpenAI-compatible provider 后研究一个小宇宙/RSS 示例。

抖音、GPU 转录、飞书和 Pages 分别提供独立启用与验证步骤。

## 7. GitHub Pages 设计

公开版延续“源码仓库与内容仓库分离”的架构：

1. 用户创建自己的独立 Pages 仓库。
2. 初始化命令克隆或绑定该仓库到 `data/github-pages/`。
3. 应用将 Markdown 转换为静态 HTML，并只允许同步白名单类型。
4. 同步前执行路径与内容敏感信息检查。
5. 默认只生成和本地提交；自动 push 必须由用户显式启用。

公开源码仓库的 GitHub Actions 不运行抖音采集、媒体下载、ASR、Whisper、Ollama 或内容发布任务。

## 8. 脱敏与安全门禁

### 8.1 路径审计

阻止运行数据、配置、备份、缓存、构建产物、私有仓库元数据和内容仓库进入公开副本。

### 8.2 内容审计

扫描并阻止：

- API Key、Bearer Token、Webhook 和数据库密码。
- Cookie、浏览器会话和认证状态。
- 个人邮箱、个人绝对路径、私有 GitHub 用户名和远程地址。
- 真实 `sec_uid`、视频 ID、已发布内容 URL、内容笔记和转录文本。
- 配置文件中非占位符的敏感字段。

示例值必须是明确无效的 `CHANGE_ME`、example 域名或测试固定值。

### 8.3 运行时脱敏

- 日志继续复用集中脱敏工具。
- 健康检查和诊断仅返回能力是否配置及连接状态，不回显秘密。
- Web 配置接口不返回已保存的密码、Cookie、Webhook 或 API Key。
- Pages 同步继续使用扩展后的文件名和文本内容双重拦截。

## 9. 许可证与第三方代码

KenRadar 自有代码使用 Apache-2.0。公开前必须对 `kenradar/vendor/douyin_downloader/` 追溯上游仓库、具体文件来源和许可证：

- 授权兼容且归属可确认的代码保留版权头，并记录在 `THIRD_PARTY_NOTICES.md`。
- 不得将第三方代码重新声明为 KenRadar 自有版权。
- 无法确认授权的文件不得进入公开版；相应能力应改为可选外部依赖，或在发布报告中明确标为不可用。

README 必须包含平台条款、Cookie 安全、内容版权和用户自行确认采集行为合规的说明。

## 10. 错误处理

- 私有功能退役若留下导入、路由、迁移或测试断链，验证必须失败，不能进入公开导出阶段。
- 公开导出若命中敏感路径、敏感内容、未知大文件或许可证不明文件，必须中止并给出文件级报告。
- Docker 启动时可选服务缺失应表现为可诊断的降级状态；PostgreSQL 或核心配置缺失则健康检查返回 not ready。
- Pages 未初始化、工作区不干净、发现敏感候选或 Git 操作失败时，禁止提交或推送。
- 所有外部 API 失败继续生成明确降级结果，不得将原始转录伪装为成功摘要。

## 11. 验证计划

### 11.1 私有仓库

- `python -m compileall kenradar scripts`
- 完整 pytest。
- 前端 `npm run lint` 与 `npm run build`。
- 全仓搜索退役功能符号，确认无产品入口和运行时导入。
- 在现有 PostgreSQL 上执行迁移状态与核心真实查询检查，不修改实验表数据。
- 重启并验证 health、dashboard、content、sources、insights 和 SSE。
- 本地生成 Pages，并仅执行 GitHub 同步 dry-run。

### 11.2 公开副本

- 从空目录执行 Docker Compose build/up。
- 验证数据库初始化、`doctor`、健康检查和 Web。
- 验证缺少所有可选凭据和 GPU 服务时的安全降级。
- 完整后端测试、前端 lint/build 和容器 smoke test。
- 秘密、个人信息、许可证、依赖漏洞和导出白名单检查。
- Pages 初始化、静态生成和本地 Git 提交验证，不推送。
- 确认公开仓库只有新历史，且不包含私有 Git 对象、远程或提交作者历史。

## 12. 提交与发布顺序

1. 在私有仓库创建实验功能退役提交。
2. 在私有仓库完成生产链路验证并记录结果。
3. 生成公开副本并完成开源部署、文档和审计改造。
4. 在公开副本初始化新 Git 历史并创建本地提交。
5. 输出发布报告：保留能力、删除能力、敏感项检查、验证结果、许可证状态和待用户配置项。
6. 等待用户明确授权后，才可创建 GitHub 远程仓库或推送。

## 13. 成功标准

- 当前私有仓库不再暴露公司研究、财务分析或 NotebookLM 产品能力。
- 当前私有生产数据库、数据目录、远程仓库和 Pages 发布功能未被破坏。
- 公开副本可通过 Docker Compose 从空环境启动并完成基础研究流程。
- 公开副本不包含真实秘密、个人数据、内容数据、私有历史或机器绑定路径。
- GitHub Pages 独立仓库流程有明确初始化、验证和安全保护。
- Apache-2.0 与所有公开第三方代码的授权边界清楚。
- 未经最终确认，没有任何新远程仓库创建或代码推送行为。
