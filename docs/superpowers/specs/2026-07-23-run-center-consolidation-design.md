# KenRadar 处理中心整合与任务指挥台设计

## 目标

将侧栏中功能重叠的“处理流水线”和“发布通知”合并为一个“处理中心”，以后台任务或批次为主视角，让用户优先看清：系统正在做什么、任务卡在哪个阶段、影响多少内容，以及如何安全启动修复。

本次仅重构处理中心的信息架构与局部排版，不改造全站导航结构、不更换任务编排系统，也不改变现有采集、转录、AI、发布和通知执行顺序。

## 导航与兼容路径

- 侧栏只保留一个入口：`处理中心`，图标沿用 `Activity`，异常计数继续显示在该入口。
- 主路径保持 `/run`。
- `/publish`、`/pushes`、`/logs` 和 `/run?tab=history` 继续可访问，但前端加载后统一映射到处理中心，并自动定位到对应的历史或诊断区域。
- 删除前端 `publish` 页面状态，避免同一组件被两个导航节点重复挂载。
- 不删除既有后端发布、推送、重试和日志接口。

## 页面信息架构

页面采用单列任务指挥台，由上到下分成四层。

### 1. 全局状态条

首屏顶部回答系统当前是否需要人工介入，显示：

- 调度状态与下次运行时间；
- 运行中任务数；
- 排队任务数；
- 卡住或失败任务数；
- 今日发布或通知成功数。

状态优先级为：需要修复、运行中、正常。异常状态使用警告或危险色，正常状态降低视觉噪声。保留“手动检测”操作。

### 2. 需要处理

存在失败、疑似停滞或系统告警时，该区域自动出现在任务列表之前。每个问题项显示：

- 任务名称、任务类型、批次 ID；
- 当前阶段和卡住时长；
- 错误摘要和受影响内容数量；
- 资源状态或阻塞原因；
- 从卡点重试、查看诊断、查看任务详情操作。

修复采用分级策略：

- 单任务从失败阶段重试可以直接提交；
- 批量重试、从下载阶段全部重跑、重启 Web 等高影响操作必须二次确认；
- 提交后立即显示受理状态，最终状态仍以服务端任务数据为准；
- 接口失败时保留问题项并显示错误，不将按钮点击伪装成修复成功。

### 3. 任务列表

页面主体以后台任务或研究批次为单位，排序固定为：

1. 卡住或失败；
2. 运行中；
3. 排队；
4. 最近完成。

每个任务卡片默认展示：

- 任务名称、类型、ID、开始或完成时间；
- 总进度、成功/失败/等待内容数；
- 当前阶段和最近状态变化；
- 横向阶段链：`发现 → 下载 → 转录 → AI 整理 → 笔记 → Pages 发布 → 飞书通知`。

阶段状态使用已完成、运行中、等待、失败和跳过五种明确表现。小屏幕下阶段链允许水平滚动或换行，不压缩成不可辨认的图标。

展开任务卡片后显示：

- 各阶段计数和耗时；
- 当前队列通道、并发容量与等待量；
- GPU/AI 资源锁及持有者；
- 与该任务相关的最近日志；
- 失败内容明细和逐项修复入口。

默认只展开一个任务，避免多个长详情同时撑乱页面。用户主动展开的任务在本次页面会话中保持展开。

### 4. 历史与诊断

低频信息放入页面底部默认折叠的标签区：

- 发布记录；
- 系统告警；
- 运行日志；
- 模型与 GPU。

从兼容路径 `/publish` 或 `/pushes` 进入时自动打开“发布记录”；从 `/logs` 进入时自动打开“运行日志”。发布记录继续显示 Pages 和飞书结果，不再作为独立功能页面。

## 卡点识别

卡点分为两级：

- `失败`：任务、任务步骤或内容已有明确失败状态；
- `疑似停滞`：任务仍为活动状态，但当前阶段在合理时间内没有状态更新。

首版优先使用现有任务状态、步骤状态、更新时间、运行时间线和错误字段。只有在前端无法获得阶段更新时间时，才对现有状态接口补充最小只读字段，不新增独立状态存储。

疑似停滞不能自动触发修复。阈值应按阶段区分或使用现有任务超时配置，避免把长视频转录、Agnes 限流等待或 GPU 排队误判为失败。无法可靠判断时展示“运行时间较长”，不展示确定性的“卡住”。

## 组件边界

保留 `RunCenter` 作为页面容器，并将职责收敛为以下组件：

- `RunCenterSummary`：全局状态和核心数字；
- `AttentionQueue`：失败、停滞和告警；
- `TaskCommandList`：任务排序、筛选和展开状态；
- `TaskCommandCard`：单任务阶段链与摘要；
- `TaskDiagnostics`：队列、锁、日志和失败内容；
- `RunCenterHistory`：发布、告警、日志、模型/GPU 标签区。

`RunCenterModel` 负责把现有 `videos`、`tasks`、`system`、`alerts` 和 `pushRecords` 归一为页面模型，组件不重复推导业务状态。能复用的 `TaskProgress` 和状态 token 继续复用。

## 数据与刷新

- SSE 继续承担研究任务状态更新；断线时沿用现有轮询降级。
- 数据库和服务端接口始终是最终事实来源。
- 页面不因一次局部接口失败整体白屏；状态摘要、任务列表和历史诊断分别显示局部错误。
- 修复请求成功受理后刷新权威任务数据，不在客户端预设最终成功状态。
- 发布成功数使用真实推送或发布记录，不使用“推荐推送”代替。

## 验收标准

- 侧栏只出现一个“处理中心”，异常计数不重复。
- `/run`、`/publish`、`/pushes`、`/logs` 和 `/run?tab=history` 均能进入统一页面的正确区域。
- 用户在首屏能识别运行中、排队、失败和发布成功数量。
- 异常任务出现在正常任务之前，并明确显示阶段、原因和修复入口。
- 单任务修复可直接提交；高影响操作具有二次确认。
- 任务阶段链覆盖发现、下载、转录、AI、笔记、Pages 和飞书。
- 桌面与移动视口下任务列表、展开详情和修复操作可用。
- 深浅主题下运行、等待、失败、成功状态均可区分。
- 前端 lint/build、相关模型与组件测试、既有 API 契约测试通过。
- 真实 PostgreSQL 路径下至少验证一个运行任务、一个失败或模拟失败任务及一次修复受理。

## 非目标

- 不重构 workflow 或持久任务表；
- 不新增自动修复守护进程；
- 不改变 Agnes、GPU、转录和发布调度策略；
- 不删除历史兼容 URL 或后端接口；
- 不进行全站视觉重构。
